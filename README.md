# PolicyForge

> **Test policies before they reach people.**

PolicyForge is an AI-assisted, Chennai-focused policy decision-support platform. It helps users describe a local policy challenge in plain language, explore policy options, and understand potential trade-offs before real-world implementation.

It combines a 10,000-agent synthetic simulation, transparent Chennai Census 2011 population anchoring, ward-aware targeting, and Gemini-assisted policy design. It is a decision-support tool—not a forecast of real people or a substitute for government, legal, engineering, or budget decisions.

## What PolicyForge does

1. A user describes a policy problem and selects the outcomes that matter most.
2. The AI Planner identifies the appropriate analysis route automatically.
3. A supported policy is compared against alternatives and compatible two-policy combinations, then simulated.
4. A policy outside the supported catalogue is represented as a clearly labelled Gemini assumption-driven scenario rather than being incorrectly forced into an unrelated preset.
5. The Results page brings together the AI proposal, policy rationale, income-group effects, baseline-versus-policy charts, trajectories, ranges, assumptions, and limitations.

The planner opens with a blank policy question and no selected priorities, so each analysis starts from the user's own context.

## Current policy catalogue

The validated simulation catalogue includes:

- Water rationing and water-service restoration
- Energy rationing and energy-service restoration
- Rent and zoning change
- Public transport subsidy
- Public subsidy

For supported policies, PolicyForge can compare individual policies and supported two-policy bundles. It runs with 10,000 synthetic agents by design.

## Results and evidence labels

PolicyForge keeps three kinds of information separate:

| Label | Meaning |
| --- | --- |
| **OBSERVED DATA** | Public-source Chennai context and population anchoring. |
| **SIMULATION OUTPUT** | Results generated by the synthetic agent model. |
| **AI ASSUMPTION-DRIVEN SCENARIO** | A Gemini-generated, bounded hypothetical profile for a policy outside the validated catalogue. |

The `chennai_census_2011` population preset uses observed Chennai Census 2011 population data to anchor sample scale. Agent behaviour, income bands, stress, trust, compliance, and policy response are synthetic modelling assumptions.

The Results page compares a policy outcome with a no-policy baseline. For regular catalogue policies, its displayed range is based on five paired seeded runs; it is not a statistical confidence interval or empirical forecast. For AI assumption-driven scenarios, the assumptions are shown explicitly and are not presented as observed effects.

## Income groups and ward targeting

Results report separate synthetic impacts for low-, middle-, and high-income groups. A negative change in stress is favourable; changes are always relative to the relevant synthetic baseline.

The Ward Map uses official Greater Chennai Corporation ward boundaries. Users can select one or more wards on the map, or leave the selection empty to apply a policy citywide. Ward overlays are **SIMULATION OUTPUT**, based on a transparent synthetic allocation of agents to official geography; they are not observed ward outcomes.

## Gemini-assisted planning

Gemini is used server-side only for:

- Interpreting a policy request into a bounded, supported configuration
- Writing an AI policy proposal
- Classifying requests that do not fit the preset catalogue
- Preparing transparent assumptions for outside-catalog exploratory scenarios

The simulation engine, policy limits, and output validation remain within PolicyForge. Gemini does not supply unvalidated simulator metrics.

The default Gemini-only fallback order is:

1. `gemini-3.6-flash`
2. `gemini-3.5-flash`
3. `gemini-3.5-flash-lite`
4. `gemini-3.1-flash-lite`

The fallback models use the same prompt and JSON validation contract. They cannot bypass a project-wide Gemini quota limit, so an exhausted Google project quota can temporarily make AI features unavailable.

## Run locally

### Backend

PowerShell:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt

$env:POLICYFORGE_SESSION_ONLY = 'true'
$env:POLICYFORGE_AI_MODE = 'gemini'
$env:GEMINI_MODEL = 'gemini-3.6-flash'
$env:GEMINI_API_KEY = Read-Host "Paste your Gemini API key"

python -m uvicorn app.main:app --reload --port 8001
```

When prompted, paste only the Gemini key—do not include `GEMINI_API_KEY=` or quotation marks.

### Frontend

Open a second terminal:

```powershell
cd frontend
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000).

To use the local rule-based interpreter instead, set `POLICYFORGE_AI_MODE` to `rule_based` and omit `GEMINI_API_KEY`.

## Private Vercel deployment

The root [vercel.json](vercel.json) deploys both services as one Vercel Services project:

| Service | Repository root | Public route |
| --- | --- | --- |
| Next.js interface | `frontend` | `/` |
| FastAPI backend | `backend` | `/api/*` |

The browser uses same-origin `/api` routes in Vercel. Do **not** set `NEXT_PUBLIC_API_URL` in Vercel, and never expose an API key through a `NEXT_PUBLIC_*` variable.

Add these variables to the **backend service** for Production:

| Name | Value |
| --- | --- |
| `POLICYFORGE_SESSION_ONLY` | `true` |
| `POLICYFORGE_AI_MODE` | `gemini` |
| `GEMINI_API_KEY` | Your Gemini API key |
| `GEMINI_MODEL` | `gemini-3.6-flash` |
| `GEMINI_FALLBACK_MODEL_1` | `gemini-3.5-flash` |
| `GEMINI_FALLBACK_MODEL_2` | `gemini-3.5-flash-lite` |
| `GEMINI_FALLBACK_MODEL_3` | `gemini-3.1-flash-lite` |
| `POLICYFORGE_ACCESS_PASSWORD` | A strong shared access password |

Vercel deployments are stateless: results stay in the browser's current session and no database is required. The application password gate is optional and reversible—delete `POLICYFORGE_ACCESS_PASSWORD` and redeploy to disable it.

## Data scope and limitations

PolicyForge deliberately does not fabricate missing observed data or claim that synthetic behaviour is measured Chennai behaviour.

The observed-data layer includes normalised Census 2011 population context and selected Chennai public-agency context metrics. Some ward-level, housing, amenity, and historical-report tables remain catalogued but are not normalised. See [CALIBRATION.md](CALIBRATION.md), [ARCHITECTURE.md](ARCHITECTURE.md), and [VERCEL_DEPLOYMENT.md](VERCEL_DEPLOYMENT.md) for more detail.
